## [Unreleased]

> Several improvements in this cycle were informed by studying other Roslyn MCP servers — in particular
> [JoshuaRamirez/RoslynMcpServer](https://github.com/JoshuaRamirez/RoslynMcpServer) (load timeout, position-first resolution),
> [MarcelRoozekrans/roslyn-codelens-mcp](https://github.com/MarcelRoozekrans/roslyn-codelens-mcp) (dropped-reference detection),
> and [darylmcd/Roslyn-Backed-MCP](https://github.com/darylmcd/Roslyn-Backed-MCP). Techniques only; no code was reused.

### Added
- **Optional `projectPath` on every tool (phase 2)** — the symbol-by-name and project-wide tools still required `projectPath`, and a solution path was refused (`solution_needs_project`) or, earlier, silently answered for the solution's first project. Now no tool requires it. A tool that names a symbol (`roslyn_get_member_body`, `roslyn_find_references`, `roslyn_find_callers`, `roslyn_get_call_graph`, `roslyn_get_type_members`, `roslyn_find_overloads`, `roslyn_get_type_dependencies`, `roslyn_get_type_hierarchy`, `roslyn_find_implementations`, `roslyn_get_symbol_definition`, `roslyn_get_symbol_documentation`, `roslyn_preview_rename`, `roslyn_change_signature`) finds the project that declares it, in the default solution or one given: the frameworks of a multi-targeted project count as one, a symbol of a referenced assembly is taken from the first project that sees it, and a name declared in several projects is never resolved by preference — the call fails with one candidate per project, each with the `project` to pass back (or asks the user, with `--elicit`). `roslyn_get_diagnostics`, `roslyn_list_types` and `roslyn_find_unused` cover every project of a solution and name the project on each item (`project`; `Lib.Greeter [Lib]` for types); `roslyn_get_project_info` returns `{ solution, projects }` for a solution and the single-project shape otherwise. `roslyn_check_syntax` with `includeSemantics` takes a new `filePath` to name the project, and says so when neither is given. `roslyn_apply_rename` and `roslyn_apply_signature_change` take the workspace from the token. RMCP009 now requires `string? projectPath = null` on every tool, and the `ProjectPathDescription` constant is gone (#296).
- **`roslyn_info` reports the default workspace** — an agent could not find out what an omitted `projectPath` stands for, short of reading it off result paths. `roslyn_info` now returns `default_workspace`: the solution or project (`path`), or why there is none (`unavailable`), with the root it was looked for in and the setting that chose it (`root_source`: `--root`, `positional argument`, `ROSLYNMCP_ROOT` or `server working directory`). It reads the cached answer and loads no workspace (#298).
- **`roslyn_list_refactorings`, `roslyn_preview_refactoring`, `roslyn_apply_refactoring` — Roslyn's own code refactorings, headless** — the server could run no refactoring: Move type to file, Extract method, Introduce local and the rest of Visual Studio's Ctrl+. menu were out of reach, so agents retyped code by hand (#387). The three tools run Roslyn's `CodeRefactoringProvider`s through one MEF composition the server now owns (`MefHostServices.DefaultAssemblies`, which includes the new `Microsoft.CodeAnalysis.CSharp.Features` reference; both workspace kinds are created with it): list says what applies at a caret or selection, with each action's provider and source, and sets aside what a headless host cannot run (dialog-driven actions, actions that change more than documents) with the reason; preview computes one action into a unified diff and a token, naming the files it creates or deletes; apply commits it with the crash-safe physical apply the other two-step tools use. Providers come from four kinds of source: Roslyn's built-ins, the server's bundled fixers, the project's analyzer references (NuGet analyzer packages and `<Analyzer Include>` items, reflected from the same shadow copies the diagnostics tool loads), and the entries of the user's `config.json` and the committed `.madq_roslynmcp.json` — a NuGet package from the local cache, or an assembly path, which a committed file may name but which loads only with `--trust-project-providers` / `ROSLYNMCP_TRUST_PROJECT_PROVIDERS=true` or the user file's `trustProjectProviders`. `--code-actions off` / `ROSLYNMCP_CODE_ACTIONS=off`, or `"codeActions": { "enabled": false }` in either file, turns it all off with a structured `providers_disabled`; `builtIn`, `projectProviders` and a `deny` list (by export name, type name or stem such as `InvertIf`) narrow it; the two files' lists merge. A provider that throws is reported, the others still answer; whatever an `AdhocWorkspace` cannot provide (project providers) is said in the source report rather than skipped. `roslyn_info` reports the composition and every source loaded with its yield and problems, and `setup-project` prompts for the project file's `codeActions` section. (#389)
- **Development host: a new server build under running sessions** — loading a new build of the locally installed server meant ending every session first, since on Windows a dotnet tool cannot be replaced while it runs. `src/RoslynMcp.DevHost` is a development-only process an MCP client launches in place of the server: it starts the build a pointer file names and forwards stdio unchanged. `scripts/Publish-DevServer.ps1` publishes the working tree into a directory of its own and writes the pointer, and every running host swaps to that build at its next idle moment, after the new server has answered the client's replayed `initialize`; a build that does not run is refused and the session keeps its server. `-Restart` starts the same build again in every session. Not in the tool package: `dotnet tool install` gives the plain server, and nothing edits a client configuration. See `docs/development/DEV_HOST.md`. (#426)
- **TestHarness: slow tests are opt-in locally** — the check that a workspace load waits out its timeout (#379) takes about 20 s, because the server's load timeout cannot go below 10 s, and it ran in every local run. A test can now be marked `Slow`: a local run skips it, says so on the summary line (`9 skipped (1 slow: --slow runs it)`), and runs it with `--slow` or a `--test` that matches it. A CI runner (`GITHUB_ACTIONS=true`, the variable the harness already used for setup-unavailable skips) always runs it, so pull requests and the release gate keep the coverage without any workflow change.
- **The log names the exception when a tool call throws** — a tool that threw logged only `unhandled exception`, and a call that failed before its tool ran (an argument the SDK could not bind) left no log entry at all, while the client got the SDK's opaque `An error occurred invoking '<tool>'.` either way, so neither side could say what went wrong. A `tools/call` request filter now gets the exception into the log: the tool's entry reads `unhandled IOException: <message>`, and a call that never reached its tool gets an entry `failed before the tool ran: <exception>` with its arguments. What the client sees is unchanged. (#371)
- **TestHarness: run part of the suite, and the full suite on every pull request** — a full harness run takes about three minutes and was the only verify step, even for a change whose tests sit in one group; `--only-build-diag` was the one way to run less. `--only <a,b>` now builds and runs only the groups whose name contains one of the parts, `--test <text>` keeps the matching tests, and `--list` prints the groups. Groups that are not selected are not built either, since some start servers or create projects while being built: `--only DefaultWorkspace` takes 15 s. A part that matches no group fails with exit code 2, and a filtered run says so on its summary line, so it can never pass for a full one. The default output now prints each group's time and the slowest groups. The two `DotnetRunner` gate checks moved from *Workspace Hygiene* into a *Dotnet Runner* group, and the log reading they share with *Linked Files* moved to `ServerLog`, whose minimum entry count is now per caller — a filtered run writes far fewer entries than the full-run floor of 50. `harness.yml` now runs the full suite on pull requests to `dev` and `main` (Windows and Linux; macOS stays at publish and by hand, its runners queue for up to an hour), so a filtered local run no longer leaves a change untested. `AGENTS.md` says when a full local run is still needed. (#367)
- **`line` and `column` on `roslyn_replace_in_code`** — the tool selects nodes by kind and name, which cannot single out one of several similar nodes: the third `if` in a method needed a text fragment that happened to be unique, or `force=true`, which replaces all of them. `line` (with `column` for several nodes on one line) now picks the node starting there, the position a read of the file or a dry run's `changed_nodes` already shows. Both narrow `nodeKind` and `textPattern`, and a position where no such node starts matches nothing rather than the nearest node. A position is only as good as the read it came from: after an edit moves lines it can land on a different node of the same kind, so re-read first, or add `textPattern`. This replaces the node map proposed in #356, which would have added a new address to learn that goes stale in the same way. (#356)
- **`roslyn_get_symbol_info` reports what the compiler knows about the expression** — the tool returned a symbol's kind, name and type and dropped the facts agents most often get wrong. It now also returns the flow-adjusted type, nullable flow state (`NotNull` / `MaybeNull`), the implicit conversion and converted type, the constant value, and on a failed overload resolution the candidates and reason; `includeOverloads` lists the method group. A position on a method name describes the call. Nullability is decided per position, so a `#nullable enable` section works in a project that has it off, and `nullable_context: "disabled"` keeps a missing flow state from being read as not-null. Declarations now resolve too: a class name or a local's declaration used to fail with "No symbol resolved". Existing fields are unchanged and new ones are omitted when empty. (#354)
- **`roslyn_analyze_region`** — new read-only tool returning the compiler's data-flow and control-flow facts for a line range: variables declared, what flows in and out (an extracted method's parameters and return values), definite assignment, captures, reachability of the start and end, and the jumps and explicit `throw` sites in the region. These are facts an agent can only guess at from text, and they cost a few dozen tokens. A range resolves to whole statements from one statement list, widening a partly covered statement and reporting the lines analyzed; an expression body or initializer is analyzed as one expression and has no `control_flow`. Fields and properties are outside Roslyn's data-flow analysis, so they never appear. (#352, #353)
- **Per-worktree workspace rooting via committed `.github/mcp.json`** — using the server across git worktrees required hand-editing the global `~/.copilot/mcp-config.json` and reloading: global, fragile, and it left a file lock on the worktree on teardown. A committed `.github/mcp.json` now defines the `MadQ.RoslynMcp` server with `--root .`. Copilot CLI loads project-level MCP config per checkout and it overrides the global definition by name, so every worktree self-roots at session launch with no global edits — `.mcp.json` stays gitignored for per-checkout local overrides. `AGENTS.md` documents entering a worktree as a session (`/fork worktree`) rather than a bare `git worktree add`, since a running server does not re-root. (#359)
- **Release gate: the TestHarness on Windows, Linux and macOS** — a release was not gated on tests on any operating system: `publish.yml` only checked that the server publishes for three RIDs, and the harness step in `build.yml` has been commented out since March. `.github/workflows/harness.yml` now runs the harness with `--quiet` on `windows-latest`, `ubuntu-latest` and `macos-latest`, and `publish.yml` will not publish (or complete a dry run) unless all three pass. It can also be run by hand on any branch and runs on a pull request that changes the workflow itself; it does not run on every push — `build.yml` is unchanged. macOS had never been tested before; its first run failed 64 tests for one reason, the boundary bug listed under Fixed. (#330)
- **TestHarness `--quiet`, and a Linux run under WSL** — a harness run printed about 350 lines for 239 tests, nearly all of them passing lines that say nothing; agents filtered it with text matches that also caught passing tests with "error" in their name. `-- --quiet` now prints nothing for a passing test, one line per failing test with its group (followed by the server's stderr), and exactly one summary line (`PASS  239 passed` / `FAIL  238 passed, 1 failed`); the server build output appears only when the build fails. Default output and the exit code are unchanged. `scripts/Test-HarnessWsl.ps1` runs the same harness on Linux from a Windows machine: it copies the working tree (uncommitted changes included, without `bin`/`obj`/`.git`) into the WSL filesystem and runs it there with the SDK `global.json` pins (`-InstallSdk` installs that version into a private directory). Until now nothing ran the harness off Windows, so platform-only tests — Unix file modes, symlinks — checked nothing. `AGENTS.md` says when the Linux run is needed. (#325)
- **Optional `projectPath` via a session default workspace (phase 1)** — the required `projectPath` on every tool was suspected of pushing agents toward built-in `Grep`/`Read`/`Glob`, and in practice it has the same answer for a whole session. Search (`roslyn_search_files`, `roslyn_semantic_search`, `roslyn_find_string_literal`, `roslyn_list_files`), read/structure (`roslyn_read_file`, `roslyn_get_line_count`, `roslyn_get_file_outline`, `roslyn_get_symbol_info`, `roslyn_get_usings`, `roslyn_get_symbols_in_scope`, `roslyn_get_trivia`, `roslyn_check_drift`), editing (`roslyn_replace_in_code`, `roslyn_replace_in_file`, `roslyn_insert_lines`, `roslyn_write_file`, `roslyn_local_history`), code-fix (`roslyn_preview_code_fix`, `roslyn_apply_code_fix`), and build (`roslyn_build_project`, `roslyn_clean_solution`, `roslyn_restore_packages`) tools now accept an omitted `projectPath`. It resolves to a default fixed by startup inputs only — `--root <path>` (or a bare positional path, so the long-documented `"args": ["."]` finally does something) > `ROSLYNMCP_ROOT` > server CWD — then to the one `.sln`/`.slnx` there (`"solution"` in `.madq_roslynmcp.json` picks among several), the nearest solution above, or the single `.csproj`. It never depends on which workspaces are cached, never searches downward, rejects drive roots and system directories, and never falls back to an AdhocWorkspace; with no usable default the call fails with `missing_project_path` and a `--root` hint. File-based tools pick the project in the default solution that owns `filePath`, so a file in any project works. `.sln`/`.slnx` paths are accepted as an explicit `projectPath`, and build/clean/restore then target the whole solution (the Roslyn fast path checks every project). RMCP009 now pairs `string projectPath` with `ProjectPathDescription` and `string? projectPath = null` with `OptionalProjectPathDescription`. Symbol-by-name and aggregate tools follow in phase 2 (#296). (#295)
- **Position-based symbol resolution** — `roslyn_find_references`, `roslyn_find_callers`, and `roslyn_preview_rename` accept optional `filePath`+`line`(+`column`) to pinpoint one specific overload, local, or parameter instead of resolving by name.
- **Opt-in analyzer diagnostics** — `roslyn_get_diagnostics` gains `includeAnalyzers` to also run the project's analyzer references and include their findings; analyzer failures degrade to compiler-only output with an explanatory hint.
- **Configurable workspace load timeout** — MSBuild loads are bounded by `ROSLYNMCP_LOAD_TIMEOUT_SECONDS` (default 300; `0` disables) instead of hanging indefinitely when MSBuild wedges.
- **Post-load reference validation** — loads detect projects whose metadata references were silently dropped by a contended design-time build, retry once on a fresh workspace, and surface anything persistent via `load_warnings` on `roslyn_get_project_info`.
- **`roslyn_check_drift`** — new read-only tool that detects FileSystemWatcher misses (network drives, buffer overflow) by comparing on-disk timestamps against the workspace's last sync, reporting drifted or deleted files with a hint to resync via `roslyn_respawn`.
- **Load benchmarks** — `benchmarks/RoslynMcp.Benchmarks` BenchmarkDotNet suite measuring cold solution load, warm compilation cache hits, incremental text-change recompiles, and solution-wide reference search, with a recorded baseline in `benchmarks/BASELINE.md`.
- **Project-local server settings (`.madq_roslynmcp.json`)** — `setup-project` now also offers to write a commit-worthy server config at the repo root, so a team shares per-project preferences instead of every contributor hand-setting global config. The server discovers the file by walking up from each request's resolved project path (startup CWD is unreliable across MCP clients) and fills in `elicit` and `workspace` where no CLI arg or env var was given — precedence: CLI arg > env var > project file > built-in default. Machine-specific settings (log/MSBuild/backup paths) and `preload` are deliberately never read from the committed file. Reruns of `setup-project` preserve earlier choices and unknown keys; `FindRepoRoot` now also recognizes worktree/submodule checkouts where `.git` is a file. (#220)
- **Visual Studio version pin (`--vs-version` / `ROSLYNMCP_VS_VERSION` / `vsVersion`)** — legacy (non-SDK) .NET Framework projects still failed with the `Microsoft.Build.Shared.XMakeElements` type-initializer crash on machines whose newest Visual Studio is 2026 (18.x), even with the #258 BuildHost pin. The pin did exactly what it said — the BuildHost log read `Registered MSBuild 9999.0 instance at E:\Dev\Vs18` — but bare `vswhere -latest` and the BuildHost's own `OrderByDescending(Version)` agree on "newest", so in `vs` mode the pin re-selected the crashing instance, and in `auto`/`sdk` mode no pin was applied at all. The only escape was `--msbuild-path`, a machine-specific path that `ProjectConfig` rightly refuses from the committed file. `--vs-version 17` (or `17.14`, or a raw vswhere range like `[17.0,18.0)`) now passes `-version` to vswhere; in `vs` mode it selects the server's instance and fails with a message naming the pin when nothing matches, and in `auto`/`sdk` mode it steers only the .NET Framework BuildHost — the part that actually loads legacy projects — while the server keeps the .NET SDK. A version is portable, so unlike `msbuildPath` it is honored from `.madq_roslynmcp.json` (`"vsVersion": "17"`), and `setup-project` offers it when the workspace mode is `vs`. `--msbuild-path` still wins; `adhoc` ignores it; a malformed pin is logged at startup instead of silently dropped. Precedence: CLI arg > env var > project file > newest installed. (#265)
- **`roslyn_apply_code_fix` and `roslyn_preview_code_fix`** — two new refactoring tools for applying Roslyn code fixes by diagnostic ID. `roslyn_preview_code_fix` shows a unified diff and returns an approval token. `roslyn_apply_code_fix` commits the fix (or a subset of fixes) with the approval token, supporting multi-fix coordination (e.g. apply only fixes matching a pattern). Phase 1 of Roslyn-backed code fix workflow; providers are limited to the bundled implementations from `RoslynMcp.Analyzers` rather than project analyzer packages. (#110, #242)

### Changed
- **One helper for the three kinds of changed text document** — `PreviewFileStateBuilder` and `PhysicalSolutionApplyPlan` each handled source, additional and analyzer-config documents in three loops with the same body, so a change to the encoding, the hashing or an error had to be made three times per file, and a missed one made the kinds behave differently. Each now has one helper taking a `TextDocument` (`AddChangedAsync`, `AddWritten`). No behaviour change. (#324)
- **An `AdhocWorkspace` reads `.editorconfig`** — a directory opened without a project file had no analyzer-config documents, so Roslyn formatted the code of every refactoring and code fix there in its own defaults (four spaces, every brace on its own line, `foreach (`), whatever the directory's `.editorconfig` said; in a project the same file was honoured. The ad-hoc project now takes every `.editorconfig` under its root, found in the walk that finds the sources, and those in the directories above it, which is what a build hands the compiler for a project. They are kept current like the sources: one written, changed or deleted under the root is picked up by the watcher and by the server's own writes. One above the root is read at load. As in a project, such a file now also sets diagnostic severities in an `AdhocWorkspace`. A harness test pins the promise `AGENTS.md` makes for both workspace kinds: with a private, gitignored `.editorconfig`, Extract method and a code fix write tabs, the configured brace placement and `foreach(`. The MSBuild case already held and needed no change. (#413)
- **`roslyn_list_refactorings` no longer repeats the whole provider source report** — every list carried `providerSources`, one entry per source with its origin path: about 1,300 tokens on this repo's seventeen sources, where an answer without them is under a hundred and each action takes about ninety. It was the same report on every call, and `roslyn_info` already had it. The list now carries `providers`: how many sources stood behind it, the refactoring and fix providers they yielded together, and under `problems` only the sources that have one — a source that failed to load, or one the workspace mode cannot have, such as project providers in an `AdhocWorkspace` — each with its first problem in full, a count of further ones, and no origin path. The counts are providers as each source loaded them, before duplicates and denied providers are dropped, not actions on offer. That keeps what the report was put there for (#389): why an expected provider is not offered is still said by the call that did not offer it. The sources that loaded now cost about fifteen tokens together. A source with a problem still costs its text on every call, some eighty to ninety tokens each. On a net10 SDK project four SDK analyzer references fail to load a dependency (#421), and this repo has a fifth, so until that is fixed a list here carries an estimated 450 tokens of sources where it carried 1,300. `providerSources` is gone from the response; `roslyn_info` lists every source the server has loaded and kept, for all projects, with every problem. `roslyn_preview_code_fix` never carried the report. (#414)
- **`roslyn_respawn` ships in every build** — the tool that ends the server so the client starts a fresh one was `#if DEBUG`, yet the hints of `roslyn_get_diagnostics`, `roslyn_check_drift`, `roslyn_build_project` and the reload path named it in every build as the way to reload a workspace that loaded badly: in the published tool that was a call to a tool that does not exist, and a hint saying "restart the server" is a dead end for an agent, which has no other way to do so. It now exists in Release, exits through the host's ordinary shutdown (heartbeat removed, STOP logged, workspaces disposed, exit code 0) once the response has flushed, with a timed hard exit as the fallback, and its description says plainly that the restart is the client's — Claude Code, Copilot CLI and VS Code restart a stdio server that exits; a client that does not leaves it to the user. A harness group starts a server, respawns it, checks the response, the exit code and the STOP entry, and starts it again; nothing had ever called the tool before. The hook never suggests it. (#406)
- **Roslyn 5.3.0 → 5.9.0** — the server's `Microsoft.CodeAnalysis.*` packages move to 5.9.0, and `Microsoft.CodeAnalysis.CSharp.Features` is added: it holds the C# implementations of Roslyn's built-in refactorings and code fixes, which #389 composes. What the docs recorded as true for 5.3.0 was re-checked on 5.9.0 and still holds: `MSBuildWorkspace` cannot apply an analyzer-config change (`.editorconfig` edits still reload), and it applies text changes to source and additional documents incrementally. `RoslynMcp.Analyzers` stays on Roslyn 4.11.0, for analyzer hosts that ship an older compiler. (#389)
- **`roslyn_preview_code_fix` offers Roslyn's own fixers and may create or delete files** — the code-fix tools ran only the two fixers bundled with the server, and refused any fix that created or deleted a file (Phase 1). They now run on the same provider host as the refactoring tools: Roslyn's fixers for compiler diagnostics (add a missing `using`, generate a type or method, remove unnecessary usings, …), the fixers shipped in the project's analyzer packages, and configured providers are offered beside the bundled ones, in that order; nested actions are flattened to their leaves; a provider that throws no longer fails the preview while others have fixes. The shared change validator allows a fix to create or delete `.cs` files inside the workspace (the apply path always could), while added or removed additional and analyzer-config documents, renames, project changes and generated, linked, external or read-only files stay refused. The result names `createdFiles` and `deletedFiles`; the preview's error for a provider failure keeps its code. Roslyn's IDE analyzers (the IDE0xxx rules, which live in the Features assemblies beside their fixers) now run too — `roslyn_get_diagnostics` with `includeAnalyzers` reports them, and the code-fix preview runs them over the one document, so an unnecessary `using` (IDE0005) is found and fixed; the fixer answers to a companion diagnostic Roslyn reports at the same span, which the preview tries when the asked-for diagnostic has no fixer. Their findings are mostly info or hidden, so `severity` gains `info` and `hidden`; the default is still errors and warnings, and a note says when IDE output was left out. (#389)
- **Agent guidance names the refactoring, code-fix and analyzer tools** — the pre-tool-use hook's edit hint, `docs/AGENT-INSTRUCTIONS.md` (full, compact and the subagent block, mirrored in `AGENTS.md`), the README's *Why RoslynMcp?* and agent-instruction snippets, and `NUGET.md` knew rename and signature change as the refactoring tools and nothing of #389. They now steer an agent about to retype code toward `roslyn_list_refactorings` → `roslyn_preview_refactoring` → `roslyn_apply_refactoring`, toward `roslyn_preview_code_fix` for a diagnostic, and toward `roslyn_get_diagnostics` with `includeAnalyzers` and `severity: "hidden"` for the IDE0xxx findings. `NUGET.md` also had the tool count two releases out of date. (#407)
- **Pagination tokens are bound to their tool and query** — a token reused with a different pattern, filter, project or tool previously served the old cached results (and even the old tool's response shape when both cached strings). A mismatch now re-runs the current query from the cursor's position and page size, consistently with an expired or cleared entry, without disturbing the original query. Paging overrides remain unchanged; an explicit `take` equal to the tool's default still reads as omitted and retains the token's page size. (#316)
- **`roslyn_search_files` avoids per-line string allocations** — regex searches now scan spans of the document text and only materialize lines that match; previously every line was converted to a string before the regex check. Search results are unchanged.
- **`WorkspaceManager.Instance.cs` is split into eight files** — the nested `WorkspaceInstance` class had grown to about 3,000 lines. It is now one partial class over `WorkspaceManager.Instance.cs` (state, construction, queries, disposal) and `.Instance.Loading.cs`, `.Instance.Reload.cs`, `.Instance.Adhoc.cs`, `.Instance.Writes.cs`, `.Instance.Links.cs`, `.Instance.EditImpact.cs` and `.Instance.Watcher.cs`. Code was moved, not changed: no member was renamed, reordered within its group or edited. In a second step, the two parts that need none of the instance's state became private nested types of it: `EditClassifier` (what a changed path means for the workspace) and `LinkResolver` (where a path leads when links are followed). Each is given the workspace root, and for the first the ignore rules, and holds no reference to the instance. `PhysicalFileIndex`, used by `WorkspaceInstance` alone, moved from the namespace into it as well. `AGENTS.md` has the rule for when a type is nested.
- **`AGENTS.md`: fold work into the branch, spawn issues sparingly** — the ride-along rule allowed only small fixes, and none once a review loop had started, so review findings in a branch's own code became follow-up issues. Findings in code the branch changes are now fixed on the branch, also during review; tangential fixes ride along when they can be verified and do not raise the branch's risk. A new issue remains right for work needing its own design, a new feature surface, a higher risk tier, or enough size to bury the branch's change. The critic-pass and finding-classification rules say the same.
- **`DefaultWorkspaceTests.cs` is split into six files** — the harness group had grown to about 1,100 lines, most of them one list of 52 tests, and GitHub no longer rendered its diff in a pull request. It is now one partial class over `DefaultWorkspaceTests.cs` (fixtures, servers, teardown, `Call`/`Verdict`), `.Files.cs` (owning-project inference, file lookup and ambiguity, case rules), `.Solutions.cs` (a solution as `projectPath`), `.Apply.cs` (apply, build, clean and restore through a solution or a project's other names), `.Resolution.cs` (the default itself and the reflection tests of its rules) and `.Server.cs` (server start and stop, also used by *Parallel Load*). The locals the tests share are bundled in one private `Fixture` record, and the parts are joined in the order the tests always ran, since some depend on an earlier one. Test code was moved, not changed. (#387)
- **`roslyn_apply_rename` and `roslyn_apply_signature_change` results have the shared result shape** — both results now derive from the common result type, like every other tool's. Field names are unchanged; `error` is written first and is left out when there is none, as everywhere else. (#338)
- **BREAKING: `roslyn_read_file` and `roslyn_get_member_body` return source as raw text** — both tools used to put the code inside a JSON string (`lines` / `body`), so every tab, quote and backslash reached the model escaped, and an exact-match edit built from a read had to undo that first. The response is now a one-line JSON header followed by the source as a separate, unescaped text block: `roslyn_read_file` keeps `file`, `source`, `total_lines`, `start_line`, `end_line` and drops `lines`; `roslyn_get_member_body` keeps `symbol_name`, `symbol_kind`, `file`, `start_line`, `end_line` and drops `body`. For a partial declaration `parts` is now the part count, and each part follows as its own header line (`part`, `file`, `start_line`, `end_line`) and then its text. Lines are joined with `\n` and one newline is added after the last, so every block ends in a newline — a client may join blocks with nothing between them. Measured on this repo, the same reads are about 12% fewer characters (8–18% depending on the code). Whitespace is never elided: the text is exact per line. The log viewer renders the new peek as a header plus source. Clients that parsed `lines` or `body` must read the second content block instead. (#328)
- **Symbolic links inside a workspace are followed when they stay inside it** — the workspace boundary used to refuse every path that passed through a link inside the workspace, whatever the link pointed at. A link that resolves to somewhere inside a trusted root (the workspace, its solution directory, a referenced project) is now followed: a folder or file shared between two places in a repository works like any other. A link that leads out of the workspace is still refused, as is one that cannot be resolved or whose target has a `..` after a name (`d/../x`), because where that leads differs between operating systems. A `roslyn_local_history` restore is now put to the same boundary: it writes through a link only where the boundary allows the path, replaces a link that leads out where it sits, and is refused when the backed-up path is outside the workspace given by `projectPath` or reaches it through a linked directory that leads out. Before, a restore wrote to whatever path its token named. Both sides are compared by their resolved location, so this also holds when the workspace itself sits under a link. File walks (`roslyn_list_files`, suffix lookup of a relative `filePath`) still do not descend into linked directories — see #314. (#322)
- **Config files created by `setup` are private** — an agent config file that `setup` creates in the home directory (rather than updates) is now readable and writable by its owner only (`0600`) on Linux and macOS, since these files come to hold tokens. Existing files keep the mode they have; the committed per-project file is not affected. (#322)
- **Hook hint matched to the intercepted tool** — the pre-tool-use hook answered every intercepted built-in tool with one fixed list that was mostly read tools and recommended `roslyn_build_project`. It now names only the tools for the operation at hand, on one line: read tools for `Read`/`view`, search tools for `Grep`, `roslyn_list_files` for `Glob`, and the editing tools plus a `roslyn_get_diagnostics` check for `Edit`/`MultiEdit`/`Write`/`create`. `roslyn_build_project` and debug-only tools are never suggested, and the hint says which tools take an optional `projectPath`. Claude Code now receives the hint too (as `hookSpecificOutput.additionalContext`, with no permission decision, so permission prompts are unaffected); it used to get nothing. The server-heartbeat check now applies to both clients, and Copilot's `create` tool is recognised. (#310)
- **`page_token` is now a cursor** — passing a `page_token` back alone used to return page 1 again: the token only named the cached result set, the position still came from `skip`, and every page returned the same token, so an agent following "pass page_token to get the next page" looped on the first page. The token now carries the next position and the page size (`{id}.{skip}.{take}`), so the token alone returns the next page; each response hands out the token for the page after it, and none when `has_more` is false or the result fits one page. A non-zero `skip` or a non-default `take` still overrides the token. A token whose cache entry has expired or was cleared by an edit re-runs the query from the token's position instead of restarting at page 1. Later pages now have the tool's own shape (`references`, `matches`, `caution`, …) instead of a generic `{ items, total }`. Applies to all 15 tools that page through the pagination cache; `roslyn_get_diagnostics` already had its own cursor. (#305)
- **`roslyn_list_files` and relative `filePath` lookup skip ignored directories** — `node_modules`, `.git`, `.vs`, `packages`, `bin`, `obj`, directories the root `.gitignore` lists by plain name or root-anchored path (globs are not interpreted; a negation un-ignores what it names), and configured names are no longer listed or searched. A pattern or path that names such a directory literally still reaches it (`bin/**/*.dll`, `obj/project.assets.json`). A bare file name that exists only under an ignored directory no longer resolves. Directory links (symlinks, junctions) are no longer followed. (#309)
- **Configurable ignore list** — `--ignore <name>` (repeatable), `ROSLYNMCP_IGNORE`, or `"ignore": [...]` in `.madq_roslynmcp.json` add bare directory names the server never walks or watches. Precedence: CLI arg > env var > project file; the winning source replaces the others. (#309)

Fixtures now live in per-group temp MSBuild projects under `%TEMP%\RoslynMcp.TestHarness` (`TestFixtures.NewMsBuildProject`), written before the group's first tool call so no test waits on the watcher debounce (the two 600 ms rename waits are gone); `TestFixtures.SweepStale` removes what a killed run leaves behind; and a final `WorkspaceHygieneTests` group reads the harness server's own log and fails on any reload flagged for a path inside the repo, naming the file. ### Fixed
- **A relative `projectPath` is found under the default workspace root** — tools report paths relative to the workspace root, so that is what an agent passes back (`projectPath: "src/App"`), but a relative path was resolved against the server's working directory only. Where the client starts the server somewhere else, which is why `--root` exists, such a path was `invalid_project_path`. A relative path is now taken against the default workspace's directory when it names something there, and against the working directory otherwise, so every path that resolved before still resolves; with no default workspace nothing changes. A path that names something under both directories (`.` or `src`, with the server started in another checkout) now means the one under the default root. The path cache uses the same rule, and the log entry says `root-relative` (#298).
- **An on/off flag no longer swallows the positional root after it** — the argument reader took the token after any flag as that flag's value, so `--elicit .` or `--no-buildhost-pin .` lost the root. An on/off flag (`--elicit`, `--code-actions`, `--no-buildhost-pin`, `--trust-project-providers`) takes the next token only when it reads as on/off (`on`, `off`, `true`, `false`, `yes`, `no`, `1`, `0`), so `--no-buildhost-pin true` does not make `true` the root either, `--elicit off` is off, and `--trust-project-providers false` is no longer a grant. A root directory named like one of those tokens is given as `./on` or `--root on` (#298).
- **`roslyn_build_project` with `targetFramework` and a solution builds the projects that target it** — `dotnet build <solution> -f <tfm>` fails for every project of the solution that does not target that framework. With both given, the projects that do are built one after the other, without those another of them references, and each build is judged on its own output; when none is found the solution goes to `dotnet` unchanged (#298).
- **`roslyn_get_diagnostics` pages from one analyzer run** — the tool had a page token of its own, a bare position, and every page computed the whole result again to skip into it. The compilation's diagnostics came from its cache, but with `includeAnalyzers` every analyzer ran again: over twenty seconds a page on a solution with analyzer packages. The token did not carry the page size either, so a token passed alone fell back to pages of fifty. The tool now pages like every other one: the result is kept in the pagination cache, later pages are cut from it, and the token is a cursor that carries the position and the page size. As with the other tools, the query's arguments are repeated with the token (the old token carried the severity itself). (#435)
- **A page token no longer serves a result from before a change made outside the server** — a paginated tool keeps its result so that later pages cost nothing, and only the server's own write tools cleared that cache. A save in an editor, by the client's own edit tool or by git reaches the workspace through the watcher, which cleared nothing: the next page came from the run before the change, with its counts and line numbers, for as long as paging went on. Each kept result is now tied to the workspace it was computed from and is served only while that workspace has not changed since; otherwise the query runs again from the token's position, as it does for an entry that expired. This holds for every paginated tool that reads a workspace. (#435)
- **A file changed on disk is read into the workspace, never written back** — to take a changed file's text into a project's workspace, the watcher flush used `TryApplyChanges`, and an `MSBuildWorkspace` writes what it applies: every save by an editor or another tool was followed by a write of the same text by the server. Whatever was saved between the flush's read and that write was replaced by the older text. The flush now sets the text in the workspace without writing (`Workspace.OnDocumentTextChanged`, reached through `WorkspaceTextSetter`; a Roslyn without it falls back to the old apply). An edit that is not on disk yet is written as before. (#403)
- **A changed file that is still open for writing is read once it can be** — the server's reads keep writers out, so a file another program still had open was refused, and the flush dropped the report without a word. When that program then closed the file without a further change, the workspace kept the old text until something else touched the file. The flush now puts the path back for the next flush, for about half a minute, logs the first failure and the giving up, and reports the workspace as behind disk meanwhile so `roslyn_check_drift` sees it. The ad-hoc path does the same. (#403)
- **The server's own write of a tracked file no longer logs a workspace failure** — after writing a file, the server had the workspace take the new text through the same writing apply, so the file was written a second time. That second write was refused whenever the file was still open, and the workspace reported it as its own failure: `WorkspaceFailed — [ERROR] The process cannot access the file … because it is being used by another process`, once per write, about 35 times in a full harness run, for calls that had succeeded. The text is now taken in memory, and the file is written once. (#433)
- **A project analyzer rebuilt in place is the new build at the next call** — the caches of analyzers and providers asked for a new load when an analyzer file's time changed, but the loader knew its assemblies by path alone and handed back the one loaded first. Diagnostics, fix providers and refactorings stayed those of the first build until the server was restarted, with no sign of it; this repository's own analyzers, an analyzer reference of the server project, were the obvious case. The loader now has one load context per reference directory and gives a directory a new one when a file in it has been rebuilt. The old context stays in memory (load contexts here are not collectible), which costs one context per rebuild of an analyzer. Not covered: an analyzer whose own file is unchanged while a helper assembly beside it was rebuilt keeps the helper it has already loaded. (#418)
- **Two analyzer references of one name both load** — every project analyzer reference of the process went into one load context, which holds one assembly of a simple name. A second assembly of that name from another path failed as already loaded, also with the very same bytes: two projects on different versions of an analyzer package, in one solution or in two workspaces of one server, and one of them lost its analyzers and fix providers. Each reference directory now has a context of its own, as in Roslyn's own hosts. A dependency several locations carry is no longer taken from whichever was registered first: the one in the asking assembly's own directory wins, else the highest assembly version. (#419)
- **`roslyn_info` lists a rebuilt analyzer once** — the provider sets of project references were kept per file and modification time and never let go, so after a rebuild `roslyn_info` listed the same source twice under one name. A set stored for a file now replaces the sets of its earlier builds, for providers and for analyzers. (#425)
- **An analyzer reference whose file is missing is reported, not skipped** — a project analyzer reference naming a file that is not there (the output of a project referenced as an analyzer before its first build or after a clean, or a file gone from the NuGet cache) was passed over without a word: its fixers and refactorings were missing from every answer, its analyzers did not run, and no source and no problem said so. It is now a project source with a problem, `analyzer reference not found: '<path>'`, with the remedy that fits where the file should be: `roslyn_restore_packages` for a path under the NuGet package cache, `roslyn_build_project` otherwise. `roslyn_list_refactorings` names it under `providers.problems` and `roslyn_preview_code_fix` under `providerProblems` when it has no fix; once one of them has asked for the project's providers, `roslyn_info` lists it while the file is still missing. `roslyn_get_diagnostics` with `includeAnalyzers` says, once for the whole call, which references were not found and so did not run. The file is looked for again at every call, so a build or restore is picked up without a restart. (#424)
- **`roslyn_preview_code_fix` says which provider sources had a problem when it has no fix** — the preview dropped the sources behind its answer, so "no code-fix provider supports it" gave no reason when the fixer was missing because its source had failed to load, or because an `AdhocWorkspace` cannot have the project's analyzer-package fixers; a source whose load failed only for the moment is not in `roslyn_info` either. A "no fixes" answer now carries `providerProblems`: each source with a problem, with its first problem and a count of further ones, in the shape of `roslyn_list_refactorings`' `providers.problems`, and its message names the switches that are off for the project (`codeActions.enabled`, `builtIn`, `projectProviders`), the plainest reason for a fixer's absence. The "code fix provider failed" answer carries the same. An answer that has a fix is unchanged. (#423)
- **`roslyn_preview_code_fix` reports a companion diagnostic's provider failure** — when the diagnostic asked for has no fixer, its companions at the position are tried; a companion whose fixer threw was dropped without a word and the answer was a plain "no fixes". The answer is still "no fixes", since a companion is any diagnostic at the position and its failure is not one for the diagnostic asked for, but the message now names the failure with the companion's id. (#423)
- **An analyzer reference that depends on another reference of the project no longer loses its types** — an analyzer assembly may need a sibling reference that the project lists after it: every SDK project lists `Microsoft.CodeAnalysis.CSharp.NetAnalyzers.dll` before `Microsoft.CodeAnalysis.NetAnalyzers.dll`, which holds its base types, and the three `Microsoft.Interop.*` generators before `Microsoft.Interop.SourceGeneration.dll`. A reference's path was made known to the loader only when that reference was loaded, so the first assembly found no dependency: on an ordinary .NET 10 project the C# NetAnalyzers lost 129 types — 43 analyzers that `roslyn_get_diagnostics includeAnalyzers` never ran, and 81 of its 85 fix providers that `roslyn_preview_code_fix` never offered — for the life of the process, and four sources carried a load problem on every `roslyn_list_refactorings` call. Every analyzer reference of a project is now registered before the first of them is loaded, as a compiler host knows all its analyzer paths up front. Also: types of a provider assembly that cannot be loaded are a problem of the source only when a provider is among them. The exported provider types are read from the assembly's metadata and each missing one is loaded by name, so the problem names the provider that was lost; helper types no provider needs (the 27 of `Microsoft.CodeAnalysis.Analyzers` that want `Microsoft.Bcl.AsyncInterfaces`, which no host on .NET has and the compiler never loads) are no longer reported on every call. (#421)
- **`roslyn_replace_in_code` no longer drops a comment in the replacement text** — the tool gave the new node the old node's trivia whole. A replacement that began with a doc comment of its own lost it, the old comment stayed above code it no longer described, and the call answered `applied: true` either way; a comment at the end of the node's line went the same way. A comment in the replacement text now takes the place of the comment attached to the node (the lines directly above it, up to the nearest blank line or `#region`, so a section heading further up or over a region is left alone), and one at the end of its last line replaces the one there (after the comma, for an enum member, and also on the last line of a file without a final line break), for every node kind. A replacement without a comment keeps the existing ones, as before, so a body-only edit need not repeat the doc comment. The blank lines and the indentation of the node's first line still come from the file. Where a comment cannot be applied safely — the existing comment is followed by a preprocessor directive, or the node does not end its line — the rest of the edit is made and `_caution` says what was left out, with the line of the node. Only the node and its comments are written: a preprocessor directive in the replacement text, and anything on the lines below its node, is named in `_caution` as well instead of vanishing (a directive is usually half of a pair whose other half stands below the node). The syntax check now parses the text that will be written, not the tree it was assembled from, so what only shows once the parts are text again is caught before the write. (#416)
- **Analyzer shadow copies hold up against several servers at once** — every server on a machine shares one shadow directory, and a client restart starts several together. The copy was a plain `File.Copy` into the final name and any file already there was taken for complete, so a server could find another's copy unfinished or held open; the load failed (`FileLoadException … being used by another process`), and the empty result was cached, so the assembly's analyzers and fix providers were gone for the life of the process — silently for anyone not reading `providerSources`. The copy is now written beside its final name and renamed into place (`FileWriter.ReplaceAtomic`), a file there is used only at the source's length, so one cut short by a process that died is replaced, and the copy carries the time it was made rather than the source's, which had let another server's startup sweep delete a copy of an old package assembly between the copy and its load. A copy of the right length that turns out to be no assembly is copied again, once, and a copy that is reused gets the current time again, so one in daily use does not age into the sweep. A load that fails for a reason another process causes and will stop causing — a file held open, one that went away, a copy another process is in the middle of — is no longer cached: the project's provider set, its analyzer set and a configured entry's set are each loaded again at the next call, at most five times for one assembly, after which the failure is kept like any other. Lasting failures (a full disk, a second assembly of a name already loaded) are cached as before. The startup sweep also removes temp files a dying server left in the shadow directory. New harness group *Shadow Copies*. (#412)
- **Preview diffs were the size of the file, not of the change** — the unified diff of `roslyn_preview_refactoring` (and of the rename, signature-change and code-fix previews, which share `SolutionDiff`) paired each new line with the earliest unused old line of the same text. One line that is common but not unique — the empty line a refactoring inserts between members — paired with an occurrence at the far end of the file, and nothing in between could match any more: Invert if on a ten-line block came out as 650 removed and 655 added lines, and two of three previews tried exceeded the client's output limit, so the agent never saw the diff it was asked to review. The matcher is now a real longest-common-subsequence: the lines both files start and end with are paired directly and the rest goes to Myers' O(ND) search, bounded at 1,500 edits per file (past that the middle is reported as removed and added). The hunk builder and the output format are unchanged. (#411)
- **A configured provider assembly rebuilt in place went stale** — the providers a `codeActions.providers` entry names (an assembly path, or a package from the NuGet cache) were loaded once per process, so an author iterating on a provider kept getting the old build until the server restarted, while a project's analyzer references were already keyed by modification time. The configured set is now stamped with what the entry resolves to — the assemblies and their modification times, or the problem that stopped the load — and a changed stamp loads it again at the next call, with one source per entry in `roslyn_info`. The same rule picks up a package that was restored into the cache after the server started. The previous load context stays in memory, as a rebuilt project analyzer's does. (#406)
- **A read in progress no longer blocks the server's own writes or fails a code-fix preview (Windows)** — every read opened its file sharing it for reading only. On Windows the server's atomic replace (a rename over the file) fails against such a handle, because it does not share for deleting; it got through only by retrying. And `roslyn_preview_code_fix`'s writability check, which opened the file for writing, failed against it once in the harness as "used by another process", with the server itself the likely holder. Every read now shares the file for reading and deleting (`FileReader.ReadSharing`), through one place: the workspace's re-reads of source files, the hash checks and the project-file parses go through `FileReader.OpenUnbounded` and `FileReader.LoadXml` (bounded by the 64 MB document limit, `.slnx` included) instead of `File.OpenRead` and `XDocument.Load(path)`. Writers are still kept out on purpose: a read that let them in could see a file half-saved in place, and the watcher flush, the edit tools and backups write what they read back to disk. `roslyn_get_line_count`, which only counts, shares with writers too (`FileReader.ObservingSharing`), so it can count a log another program is still writing. `roslyn_read_file` does not: agents copy what it returns into edits, so a file read half-saved would be written back cut short. When it, or an edit tool, is refused by another program's hold on the file (an open that does not share, or a locked byte range), the error now has a hint that says so — without guessing whose handle it is, which may be the server's own — and to retry later, instead of Windows' bare "used by another process"; `roslyn_get_line_count`'s per-file error gets the same hint. `roslyn_preview_code_fix` no longer opens each file for writing to check that it can: that open collided with any handle that kept writers out, the server's own reads included, and refused the fix over a handle gone a moment later. It checks the read-only attribute, of the file a symbolic link leads to where the document is one (and says so when the file has been deleted since it was loaded); a file that is locked when the fix is applied is reported by the apply as not written, with recovery guidance, and left as it was. (#349)
- **Whole-file reads have a size limit** — the server read files with `File.ReadAllText`/`ReadAllBytes`/`ReadLines` and `File.OpenRead`, which load whatever is there. A 1 GB log passed to `roslyn_read_file` or an edit tool took the server's memory with it, and a file with no end (`/dev/zero`) or no newline would never finish. Reads of a file a tool is pointed at, and of the server's own config, metadata and backups, now go through `FileReader`, the counterpart of `FileWriter`. Text documents Roslyn tracks and the project files MSBuild loads are read as before: both hold them whole anyway, so a limit would save nothing. It counts the bytes actually read rather than trusting the file's length, which a device reports as 0, and throws `FileTooLargeException` (an `IOException`) past the limit. There are two limits: 64 MB for content (files the tools read or edit, backups, project and solution files, agent config files such as `~/.claude.json`) and 1 MB for small metadata (git `HEAD` and refs, the run counter, the `setup-project` files). `.madq_roslynmcp.json` keeps its 64 KB and `.gitignore` its 256 KB, now enforced during the read as well. `roslyn_read_file`, `roslyn_replace_in_file`, `roslyn_replace_in_code`, `roslyn_insert_lines` and `roslyn_write_file` answer a file past the limit with `{ "error": "file_too_large", "message", "limit_bytes" }` and leave it untouched. `roslyn_write_file` also turns any other failed read of the file it replaces into a structured error instead of the SDK's opaque one. Text is decoded as before: a byte order mark selects the encoding, and UTF-8 otherwise. Symbolic links are followed as before; a link to a named pipe still blocks when opened, which is accepted (see `FileReader`). Hashes stream the file and have no limit, so a restore's conflict check still runs for a file past 64 MB. A failed read of `.gitignore` now contributes no entries, where a partial read used to keep the ones read before the failure. The log's `response_peek` serializes a result by its actual type, so fields of a derived error result are no longer dropped. (#230)
- **A project that was never restored is named as such, and a restore fixes it (#399)** — design-time builds run in Roslyn's BuildHost on the MSBuild of whatever SDK the project's directory resolves (the nearest `global.json`, else the newest SDK installed), not on the server's. A newer SDK's (11.0.100-rc.3 was seen) resolves no references at all for a project without `project.assets.json`, and reports no failure. The server called that contention and recommended `roslyn_respawn`, which repeats the same load; it spent a reload on the first load and retries on later ones; and `roslyn_restore_packages` left the broken load in place, because the assets file is written under `obj\`, which the watcher ignores. A project with no references and no assets file is now *not restored* (`projects_not_restored` on `roslyn_check_drift`, its own wording in `load_warnings` and the hints of `roslyn_get_diagnostics` and `roslyn_build_project`): the advice is `roslyn_restore_packages`, it is not retried, discarded or healed, and `roslyn_restore_packages` flags a reload of the workspace it restored. New harness group *Unrestored Projects*.
- **TestHarness: fixtures use the SDK the repo pins** — fixture projects live under `%TEMP%`, outside the repo, so its `global.json` did not reach them and each resolved the newest SDK installed. With a .NET 11 release candidate installed beside the pinned 10.0.302, the server's MSBuild loaded every unrestored fixture with no metadata references, and every fixture-based group failed on code that was fine. - **A load that MSBuild failed on a project file is unhealthy (#300)** — load health was reference health alone. The build tool checks health again against the compilations it fetched, so a reload that promotes an unhealthy workspace meanwhile cannot have its errors stop the build. Two bounds come with it, for a failure that is the project's own (an edit that broke an import, a new project whose design-time build always fails) rather than contention: a reload is no longer retried for a project the live workspace fails on too, which cost two extra loads per reload, and after four reloads in a row are discarded the next unhealthy one is promoted and reported, rather than keeping a workspace that ignores the edit and reloading every half minute for as long as the failure lasts — then retried every 30 s up to six more times, so contention that outlasted the discards still heals without an edit. A reload is discarded when it breaks any project the live workspace had working, even while another stays broken. On macOS that is every workspace under the temp directory (`/var` is a link to `/private/var`); a checkout under a junction or a symlinked folder on Windows or Linux was hit the same way. Only links *inside* a trusted root are denied now — those can point out of the workspace; the root and the directories above it are where the user put it. Found by the first macOS harness run. (#330)
- **Claude Code hook installed where Claude Code reads it** — `setup` wrote the pre-tool-use hook into `~/.claude.json`, which holds MCP server registrations; Claude Code reads hooks from `~/.claude/settings.json`, so the hook reported as "added" never ran. `setup` now writes it to the settings file and removes the stale entry it left in `~/.claude.json` (only its own entry — everything else in both files is preserved). The entry is scoped with a `Read|Grep|Glob|Edit|MultiEdit|Write` matcher instead of matching every tool call, and has a 5-second timeout instead of the 600-second default. An existing entry that already invokes `madq-roslynmcp` keeps its command (an absolute path, `--log`); one under a legacy command name is replaced. A settings file that is not valid JSON, or whose `hooks` / `PreToolUse` value has an unexpected shape, is left untouched and reported, a write failure no longer crashes `setup`, and when the old entry cannot be removed `setup` says so instead of reporting a clean install. **Rerun `madq-roslynmcp setup` to move an existing hook.** (#319)
- **Concurrent `dotnet` builds no longer race on shared `obj\` output** — agents issue several `roslyn_build_project` calls back to back or in parallel (often `forceBuild` just to check compilation); concurrent builds of projects in one solution write the same `obj\` state files, the contention behind #300. `DotnetRunner` now runs one `dotnet build`/`clean`/`restore` at a time process-wide and queues the rest, logging `queued N ms behind another dotnet command`; the reported build duration stays the process's own runtime. The `roslyn_build_project`/`roslyn_clean_solution`/`roslyn_restore_packages` descriptions now steer agents to `roslyn_get_diagnostics` for compile checks, one whole-solution call (omit `projectPath`) instead of one per project, and `forceBuild` only when diagnostics are untrustworthy. (#306)
- **`scope.Record` notes reach the log again** — `Record` appended to the entry's detail, and every terminal (`Outcome`/`Failed`/`Error`), which runs last on each return, overwrote it; no annotation recorded on a normal path was ever logged (DotnetRunner's command/cwd/exit trail, default-workspace resolution notes, cache notes). Notes are now kept separately and joined after the terminal's detail when the entry is written. (#306)
- **Startup and first load no longer walk `node_modules` and `.git`** — in a large tree the server took seconds to start, and over 30 s on a network share: past the startup timeout of MCP clients, so it never connected. Three separate causes, all fixed. (1) The generic host's default builder watched `appsettings.json` for changes under the working directory, which on Linux registers one inotify watch per directory before the host starts; the server now uses the empty host builder with the content root pinned to the install directory, and startup time no longer depends on the working directory. (2) Each workspace held one recursive file watcher on its root, which walked the same tree on the first load and again on every applied edit; the root is now split into a few watchers around the directories that can never hold a compilation input, started on a background thread, with edits made in the meantime reconciled by timestamp. On a 45,000-directory test tree the server went from 90,530 inotify watches to 13. (3) Recursive walks could not skip a directory: `roslyn_list_files`, the suffix-match fallback for a relative `filePath`, AdhocWorkspace discovery, and the large-solution warning now share one pruned walk that never enters an ignored directory, never follows a directory link, and stops at depth 32. (#309)
- **Log `workspace_mode` distinguishes SDK from VS** — TOOL entries logged `MSB` for every MSBuildWorkspace call (`isMSBuild ? "MSB" : "ADH"`), so an SDK session was indistinguishable from a VS session in the log and the log viewer. The label now comes from the MSBuild the process registered (`MSBuildBootstrap.ResolvedMode` — process-global, so every MSBuildWorkspace shares it): `SDK`, `VS`, or `ADH`. Before the first workspace load, the configured `--workspace` mode stands in; only an undecided `auto` session keeps the generic `MSB` (so tools that never touch a workspace still get a label, as the log format requires). The viewer adds hover hints for `SDK`/`VS`, colors them as the MSBuild family, and still renders `MSB` from older logs. A new `WorkspaceHygieneTests` check reads the harness server's log and requires `SDK` labels, with no `MSB` after the mode resolves. Also fixed: `TryResolveRoot` and `TryResolveSolution` never recorded the workspace mode, so tools that resolve only a root or a solution (`roslyn_list_files`, `roslyn_search_files`) logged AdhocWorkspace calls with the MSBuild label. Every resolution guard now records it, and a second hygiene check calls both tools on an adhoc directory and requires `ADH`. (#303)
- **Evicting a workspace no longer wedges every tool call** — `WorkspaceInstance.Dispose` quiesced its debounce and deferred-retry timers with `Timer.Dispose(WaitHandle)` followed by `ManualResetEventSlim.Wait()`. The timer signals the *kernel* event; the slim event's `Wait` watches only its own managed flag, which nothing sets — so the wait never returned once a timer existed, even with no callback running. `WorkspaceManager` ran that teardown inside `cacheLock` (LRU victims past their 30 s grace period via `SweepRetired`, and the loser of a load race), the lock every tool call takes to resolve its workspace, so the first eviction of a workspace whose watcher had ever fired stopped the server answering for good — a full TestHarness run reproduced 12+ minutes of silence after one project load. The quiesce now waits on a kernel `ManualResetEvent`, bounded by the existing 30 s timeout with a logged error instead of a hang; evicted instances are collected under the lock and disposed on the thread pool after it; each teardown logs `Dispose — Released '<path>' in N ms`. (#277)
- **Editing a non-compilation file no longer forces a full workspace reload** — `roslyn_insert_lines` on `CHANGELOG.md`, or `roslyn_replace_in_file`/`roslyn_write_file` on any `.md`/`.txt`/unrelated `.json`, wrote the file and then called `InvalidateFile`, whose untracked-path branch bumped `reloadVersion` unconditionally — so the next compilation-needing call paid a multi-second MSBuild reload (and, per #235, another chance for a contended design-time build to drop metadata references). The FileSystemWatcher was never the cause: its filter is `*.cs`. A single `RequiresReload` predicate now drives both `InvalidateFile` and the watcher flush: build output under `bin/`/`obj/` is dropped first (NuGet's generated `.props`/`.editorconfig` live there), a new `.cs` reloads, MSBuild evaluation inputs reload (`.csproj`, `.props`, `.targets`, `.sln*`, `.editorconfig`, `.globalconfig`, `.ruleset`, `.resx`, `global.json`, `nuget.config`, `packages.lock.json`), anything in a project's `AdditionalDocuments`/`AnalyzerConfigDocuments` reloads, and everything else is a workspace no-op (the pagination cache is still cleared). Every reload flag is now logged with path and reason (`Reload — Flagged (new document): …`) — previously the log showed that a reload happened but never which file caused it. Known limitation: MSBuild `EmbeddedResource` items are not exposed by Roslyn and cannot be recognized; they do not affect Roslyn-served results. New `ReloadFlaggingTests` harness group asserts `roslyn_check_drift.reload_pending` after each kind of write, in a temp fixture project. (#273)
- **`roslyn_replace_in_code` no longer leaves mixed line endings** — the replacement node was spliced in with the line endings of the replacement *text* (LF, as MCP clients send it), not the file's. On a CRLF file one semantic replace produced a file that was CRLF everywhere except the replaced member; `git ls-files --eol` reported `w/mixed`, `git diff` warned `LF will be replaced by CRLF`, and every touched file needed a manual re-normalize before committing. The replacement text is now normalized to the file's dominant style before parsing — the same `normalizeLineEndings` parameter (default `true`) `roslyn_replace_in_file` already has, so the behaviour is discoverable and can be switched off. The shared helper also became symmetric: a CRLF replacement into an LF file is converted to LF, where before only the LF→CRLF direction was handled. (#268)
- **`roslyn_replace_in_code` refuses a constructor whose name does not match its type** — the C# parser accepts any `Identifier(...) { }` inside a type as a constructor and leaves the name check to the compiler (CS1520), so the per-node parsing added in #267 still let a forced batch across differently named types write a `Widget` constructor into `Gadget` with a clean syntax verdict. The TestHarness case added for that scenario in #271 had been failing since merge (CI runs the build, not the harness). The check now lives in `ParseReplacement` and applies to destructors too. (#267 follow-up, found via #268)
- **`roslyn_replace_in_code` accepts constructors, and `dryRun` actually validates** — the replacement validator dispatched on a hard-coded list of node kinds; anything not on it (constructors, destructors, operators, events, indexers, enum members, delegates) fell through to `ParseExpression`, so a byte-for-byte valid constructor was rejected with `Unexpected token '{'; Invalid expression term 'bool'`. The replacement is now parsed in the grammatical position of the node it replaces: a type member inside a dummy type that borrows the enclosing type's name (and kind, for enums), so constructors parse as constructors; statements as statements; `using` directives as a compilation unit; everything else as an expression. The replacement must be exactly one node — smuggling a second member (or closing the type early) is refused. `dryRun` used to return before any parsing, so a passing dry run said nothing about whether the real write would pass; it now runs the same parse and tree validation and only skips the write. `ctor`/`constructor` are accepted as `nodeKind` aliases and `textPattern` matches constructor, destructor, event, delegate, and enum-member names properly instead of the whole node text. (#267)
- **Auto-detection judges a solution by the projects it references** — in `auto` mode a `.sln`/`.slnx` load peeked at whatever `.csproj` the file system enumerated first under the solution directory (`FindFirstCsproj`), which on a real repo was an SDK-style backup copy that sorted before the real project and was not in the solution at all. A legacy solution therefore auto-detected as `Sdk`, skipped the Visual Studio BuildHost pin, and failed to load. `DetectLoadStyle` now reads the project list from the solution file itself (`.sln` `Project(...)` lines or `.slnx` `<Project Path>` elements, text-parsed because MSBuild is not registered yet), skips projects missing on disk, and picks `Vs` if **any** referenced project is legacy — one is enough to route the load through the .NET Framework BuildHost. A solution listing nothing readable falls back to a bounded nearest-first directory scan that skips `bin/`, `obj/`, `packages/`, `node_modules/`, and dot-folders. The log line now says which file decided: `auto-detected Vs: DenseSense2022.csproj is legacy-style (DenseSense2020.sln, 5 projects)`. (#266)
- **`dotnet pack` can no longer silently produce a wrong-id package** — the dotnet-tool packaging metadata (`PackAsTool`, `PublishSingleFile=false`, the CI RID exclusion) was gated entirely on `Configuration == 'Pack'`, so packing with `-c Debug`/`-c Release` skipped it and emitted a plain `RoslynMcp.<ver>.nupkg` that `dotnet tool install MadQ.RoslynMcp` reported as "not found" — and README/INSTALLATION Option C actively instructed the broken `-c Debug`. The package identity (`PackageId`/`ToolCommandName`) is now unconditional so it can never diverge by config; a new `PackDebug` configuration packs a debug-flavored tool; a guard target fails any pack under a non-tool config with a message pointing at `-c Pack`/`-c PackDebug`; and the docs now use `-c PackDebug`. (#260)
- **Unchanged files no longer round-trip through the workspace** — a changed file's text was re-read and applied unconditionally. The only up-to-date check was a size comparison, and only for writes RoslynMcp made itself. Disk text is now compared against the document's current `SourceText` before applying, so an identical rewrite is skipped entirely — as is a same-length edit, which the size check could never catch. Applying identical text was not free: it still ran a `TryApplyChanges`, which writes to disk and flags a full reload when it fails.
- **Deleting several files flags one reload, not one per file** — the delete loop incremented `reloadVersion` unconditionally per file. Each increment moves the generation, and an in-flight reload discards its work when the generation no longer matches the one it captured, so a multi-file delete threw away a full workspace load per extra file.
- **A pending reload is now reported instead of being silently invisible** — `roslyn_check_drift` gains `reload_pending`, and `MarkSynced()` no longer runs when a flush could only *flag* a reload rather than apply the change. Previously the sync clock advanced at flag time, so the workspace could be behind disk while drift reported "in sync"; and because drift is an mtime comparison over documents the workspace already has, a newly added file was structurally invisible to it. This corrects the reasoning given in #238, which claimed drift already covered this case — it did not. (#235 follow-up)
- **A bad workspace reload no longer latches wrong symbol results** — an MSBuild design-time build that runs while another process holds a file it needs (commonly an agent writing source, or the `.csproj` itself) can silently produce projects with **zero metadata references**. Symbol queries over that workspace then return wrong-but-plausible results instead of failing. The initial load already retried once on a fresh workspace, but the reload path — the likelier victim, since it is often triggered by the very writes causing the contention — only warned, so a bad reload was promoted and stayed live until some later unrelated reload happened to succeed. `ReloadIfNeeded` now retries the same way, and **refuses to replace a healthy workspace with a reference-less one**: a stale-but-correct compilation beats a fresh-but-wrong one. The discarded reload stays pending behind a short cooldown so it retries once the contention clears, rather than costing a multi-second load on every tool call. Reference health is checked for MSBuild workspaces only — an `AdhocWorkspace` project legitimately has no metadata references. (#235)
- **Workspace load failures are now visible from the tools that show the symptom** — `load_warnings` was surfaced only by `roslyn_get_project_info`, while the symptom (a flood of phantom `CS0246`/`CS0234`) appears in `roslyn_get_diagnostics` and `roslyn_build_project`. `roslyn_get_diagnostics` now asks the workspace directly instead of inferring load trouble from error volume — so a small project producing only a handful of phantom errors is caught too — and returns `load_warnings` alongside `possible_workspace_load_issue`. `roslyn_check_drift` gains `workspace_healthy`, `projects_without_references` and `last_unhealthy_load`, making it a health probe on two independent axes: source can be perfectly in sync while the workspace holds no references. A `last_unhealthy_load` record is retained across the healing reload that clears `load_warnings`, so an episode stays diagnosable after recovery. (#235)
- **`roslyn_build_project` no longer repeats phantom errors when asked to verify them** — its Roslyn fast-path short-circuited on the same reference-less compilation, so the tool callers reach for to check whether the workspace is lying just repeated the lie, with `forceBuild: true` as the only escape. It now detects an unhealthy workspace, skips straight to a real `dotnet build`, and explains in `hint` why the fast path was bypassed. (#235)
- **`--help` and diagnostics no longer give advice that cannot work** — the `roslyn_get_diagnostics` hint said the workspace was "still resolving dependencies. Wait a few seconds and retry, or call roslyn_build_project to verify real compilation state." The state is latched until a reload, so waiting never helps, and `roslyn_build_project` reproduced the false result. The hint now names the actual remedy (`roslyn_respawn`) and, when the workspace confirms dropped references, states plainly that the errors are phantom. (#235)
- **`--msbuild-path` is honored instead of silently ignored** — the flag was parsed into `ServerArgs.MsBuildPath` and documented in `--help` and INSTALLATION.md, but nothing ever read it: `MSBuildBootstrap.EnsureReady` read `ROSLYNMCP_MSBUILD_PATH` directly, so only the env var worked and the higher-precedence CLI flag did nothing. Discovery now reads the merged `ServerArgs.MsBuildPath` (CLI arg > env var), and the override is checked **before** the mode branch, so `--workspace vs` honors it too — previously VS mode went straight to vswhere and ignored the override entirely. The path may now be a VS `MSBuild\Current\Bin` directory (which ships only `MSBuild.exe`, not `MSBuild.dll`) as well as a dotnet SDK directory. `adhoc` still ignores it — that mode skips MSBuild by design — and an invalid path still falls through to normal discovery. An empty `--msbuild-path ""` no longer masks a valid `ROSLYNMCP_MSBUILD_PATH`. (#231)
- **`--help` no longer misstates env-var precedence** — the environment-variable section was headed "override options above", contradicting the `CLI arg > env var > project file > built-in default` rule printed a few lines below it. The header now states that CLI flags win, and the list is complete: `ROSLYNMCP_MSBUILD_PATH`, `ROSLYNMCP_PRUNE_MIN_RUNS`, `ROSLYNMCP_MAX_CACHED_WORKSPACES`, `ROSLYNMCP_LOAD_TIMEOUT_SECONDS`, and `ROSLYNMCP_DISABLE_PATH_CACHE` were supported but undocumented there. `ROSLYNMCP_LOAD_TIMEOUT_SECONDS` was missing from INSTALLATION.md's table as well. (#231)
- **First `.csproj` load in adhoc mode no longer fails** — with adhoc requested (`--workspace adhoc`, `ROSLYNMCP_WORKSPACE=adhoc`, or `"workspace": "adhoc"` in `.madq_roslynmcp.json`), the first load of a path resolving to a `.csproj` crashed with a `Microsoft.Build.Framework` assembly-load error because routing consulted `MSBuildBootstrap.ResolvedMode`, which is only assigned *after* routing has committed to the MSBuild branch. Routing now also consults the requested effective mode (CLI > env > project file), so the first load goes straight to the adhoc branch; `ResolvedMode == Adhoc` remains as a fallback once the process has skipped MSBuild registration. (#229)
- **Adhoc workspaces are no longer re-loaded on every tool call** — a request whose path resolved to a `.csproj` while adhoc mode was in effect cached the workspace under its containing directory, but adhoc instances expose no `ProjectPaths`, so nothing ever mapped the `.csproj` back to that cache key. Every subsequent call missed the cache and rebuilt a full `AdhocWorkspace` (re-reading every `.cs` file under the root) only to discard it — and the same miss made `WriteAndInvalidate`/`ApplyChanges`/`InvalidateFile` fall through to unsuppressed direct writes. `GetOrLoadInstance` now aliases the requested path to whatever cache key it landed on, including when it loses the concurrent-load race. (#229)
- **VS Code Copilot `sym:` chat-reference prefixes no longer break tool arguments** — Copilot chat serializes backtick-quoted terms as `sym:`-prefixed symbol references (chat-variable form `#sym:`), which the model copies into tool arguments; one observed call reached `roslyn_semantic_search` truncated to a bare `sym:`. Symbol/type/method name parameters now strip the prefix silently (identifiers can never contain `:`; a bare prefix returns a structured error with a recovery hint). The three text-search tools stay **verbatim-first** — a `sym:`-prefixed pattern is searched as-given, and only a zero-match result triggers a stripped retry, labeled with a caution; literal searches for the text `sym:` keep working. (#228)
- **Ambiguous symbol names never mutate a silent first match** — when a name-based lookup in `roslyn_preview_rename` or `roslyn_change_signature` matches multiple symbols, the call fails with a structured candidate list (`candidates: [{ symbol, kind, containingType, filePath, line }]`) so the calling agent can retry with `containingType` or `filePath`+`line` on its own — long-running agent workflows keep moving without human intervention. Starting the server with `--elicit` (or `ROSLYNMCP_ELICIT=true`) opts into asking the user to pick interactively via MCP elicitation instead, when the client supports it.
- **`roslyn_change_signature` generates well-formed code** — the forwarding overload is now a compact expression-bodied stub (`old(...) => new(..., default);`) with correct comma/equals spacing; previously the synthesized nodes were rendered unformatted (`{returnFoo(...);}` with no space after `return`, `,bool x=false`) and the `[Obsolete]` attribute could detach from the stub. The XML doc comment stays on the updated method; the stub carries only the attribute.
- **Unified diffs no longer misalign around insertions** — the diff builder emitted context lines positionally without verifying they still matched, so lines inserted right after a change (e.g. the signature-change stub) could be swallowed as "context" and the rest of the file rendered as spurious delete/re-add churn. Hunks are now built strictly from the matched-line alignment, so context lines are matched lines by construction.
- **Metadata type lookup tolerates cross-assembly ambiguity** — `GetTypeByMetadataName` returns null when multiple referenced assemblies define the same name; lookups now fall back to `GetTypesByMetadataName`, preferring the source assembly.
- **Workspace reload for immaterial file changes** — files in `bin/`, `obj/`, `.git/`, `node_modules/`, and `packages/` no longer trigger workspace reloads; the watcher applies exclusions at debounce time for the first three directories and at the flush-decision point for `bin/`/`obj/` (which legitimately contain compilation inputs like `.AssemblyInfo.cs` and `.GlobalUsings.g.cs` that do affect the compilation if they have `docIds`). Same-length edits and identical rewrites are skipped in the text-application check. Multi-file delete batches now flag one reload, not one per file. (#239)
- **Transient mid-reload workspace faults no longer corrupt results** — editing tools (`roslyn_replace_in_code`, `roslyn_apply_rename`, `roslyn_apply_signature_change`) now return a structured `TransientWorkspaceError` (retryable, safe to retry) when an in-progress MSBuild reload is detected. The resolution path waits out transient faults transparently with bounded auto-retry (≤150 ms added latency) up to 3 attempts before surfacing the error; deterministic path-resolution failures (bad paths) bypass retries. (#247, #248, #249, #250, #251)
- **Text search tools gain unified `mode` parameter** — `roslyn_search_files` and `roslyn_semantic_search` now support `mode: "literal" | "regex" | "glob"` for flexible pattern matching (previously regex-only). `roslyn_find_string_literal` has `useGlob` / `roslyn_replace_in_file` has `useRegex` as deprecated aliases; both emit `_caution` when used and are overridden by the new `mode` parameter. Anchor-and-match `glob` dialect is consistent across tools (`*`, `?`, whole-target match). (#253, #254)
- **MSBuild BuildHost pinned to resolved VS instance** — out-of-process .NET Framework BuildHost can select a prerelease VS when multiple installs are present, causing `TypeInitializationException` on legacy projects. The server now sets `VSINSTALLDIR` + `VSCMD_VER` with a synthetic high version (derived from the resolved MSBuild bin directory) in the child environment, so the BuildHost picks the same stable instance. Applied on `--workspace vs`, auto-discovery fallbacks, and `--msbuild-path` to VS `MSBuild\...\Bin` directories. Opt-out with `--no-buildhost-pin` or `ROSLYNMCP_NO_BUILDHOST_PIN=true`. (#258, #259)
- **CI/CD: dual-publish to NuGet.org and GitHub Packages** — the release workflow now publishes the same `.nupkg` to both NuGet.org (via OIDC Trusted Publishing) and GitHub Packages (same package feed for all platforms and CI environments). The second push is gated on `!inputs.dry_run` and uses `--skip-duplicate` to tolerate package-already-exists on re-runs. (#262)

- **`roslyn_write_file`** — retries with exponential backoff (up to 3 attempts) on `IOException` due to file contention, preventing transient lock failures from surfacing as errors (#129)
